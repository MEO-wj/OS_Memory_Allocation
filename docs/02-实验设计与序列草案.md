# 02 · 实验设计与序列草案

> 本文给出三组实验序列的**具体草案**（推演已核算），可直接作为 `experiments/inputs/` 的起点。
> 原则：**两种策略从相同初始状态运行完全相同的操作**；每组 ≤ 20 步；
> 至少一组出现"空闲总量足够但最大空闲块不足"的失败。
> 最终以程序实际输出（`experiments/traces/`）为准；若人工推演与草案不符，先查规则再修订本文并注明。

## 一、输入文件格式约定

每个案例一个 JSON 文件，存于 `experiments/inputs/`：

```json
{
  "case_id": "case3-fragmentation",
  "total_memory": 90,
  "ops": [
    { "op": "alloc", "id": "A", "size": 30 },
    { "op": "free",  "id": "A" }
  ]
}
```

约束：`op ∈ {alloc, free}`；`id` 全案例唯一、不可重复 alloc；`size` 为正整数。
程序应拒绝并**保持状态不变**：重复 alloc 同一 id、free 不存在的 id、
free 已释放的 id、`size ≤ 0`、非整数、`size > TOTAL`。

## 二、三组序列草案（已手工核算）

### 案例 1：基础行为与策略分歧（★差异步出现）

目的：验证基本分配/切割/释放，并展示 FF 与 BF **选择标准不同导致布局分歧**。

```
TOTAL = 100
1. alloc A 30   A=[0,30)                                   空闲 [30,100)
2. alloc B 30   B=[30,60)                                  空闲 [60,100)
3. alloc C 30   C=[60,90)                                  空闲 [90,100)
4. free A                                                  空闲 [0,30) + [90,100)
5. alloc D 10   ★FF: D=[0,10)，剩 [10,30)   ← 取第一个够大的块
                ★BF: D=[90,100)             ← 候选 30 与 10，取最小 10，恰好整块用完
6. free B       FF 态：[10,30)+[30,60) → 仅左合并 → [10,60)
                BF 态：[0,30)+[30,60) → 仅左合并 → [0,60)
7. free C       FF 态：[10,60)+[60,90) 且右邻 [90,100) 空闲 → 双侧合并 → [10,100)
                BF 态：[0,60)+[60,90)，右邻 D 已分配 → 仅左合并 → [0,90)
```

观察点：第 5 步分歧（FF 按地址顺序 vs BF 按最小尺寸）；第 6/7 步同一操作
在两种布局下触发**不同的合并类型**——"操作相同、结果因历史布局而异"。

### 案例 2：三种合并全覆盖 + 非法操作（合并专项）

目的：一个序列依次触发仅左、仅右、双侧合并，并夹带非法释放。

```
TOTAL = 100
1. alloc A 20   A=[0,20)
2. alloc B 20   B=[20,40)
3. alloc C 20   C=[40,60)
4. alloc D 20   D=[60,80)                                  空闲 [80,100)
5. free A                                                  空闲 [0,20) + [80,100)
6. free C       C 左邻 B 已分配、右邻 D 已分配 → 独立成块    空闲 [0,20)+[40,60)+[80,100)
7. free B       B=[20,40) 左右皆空闲 → 双侧合并（三合一）    空闲 [0,60)+[80,100)
8. alloc E 55   FF=BF：唯一候选 [0,60) → E=[0,55)           空闲 [55,60)+[80,100)
9. free E       E=[0,55) 右邻 [55,60) 空闲 → 仅右合并       空闲 [0,60)+[80,100)
10. alloc F 30  FF=BF：候选 [0,60)=60 → F=[0,30)            空闲 [30,60)+[80,100)
11. free G      非法：G 不存在 → 报错，状态不变
12. free F      F=[0,30) 右邻 [30,60) 空闲 → 仅右合并       空闲 [0,60)+[80,100)
```

**仅左侧合并**的专项小例（单独成 `merge-left.json`，两策略行为一致）：

```
TOTAL = 100
1. alloc A 10   A=[0,10)
2. alloc B 10   B=[10,20)
3. alloc C 10   C=[20,30)                                  空闲 [30,100)
4. alloc D 10   D=[30,40)                                  空闲 [40,100)
5. free A                                                  空闲 [0,10)+[40,100)
6. alloc E 10   FF：第一个够大=[0,10)；BF：候选 10、60 取最小 10 → 都得 E=[0,10)
7. free B       B=[10,20) 左邻 E 已分配、右邻 C 已分配 → 独立成块  空闲 [10,20)+[40,100)
8. free C       C=[20,30) 左邻 [10,20) 空闲、右邻 D 已分配 → 仅左合并 → [10,30)
```

| 合并类型 | 覆盖位置 |
|----------|----------|
| 仅左侧 | 案例 2 第 6/7 步（BF 态）、`merge-left.json` 第 8 步 |
| 仅右侧 | 案例 2 第 9/12 步 |
| 双侧   | 案例 2 第 7 步、案例 1 第 7 步（FF 态）、案例 3 第 8 步 |

### 案例 3：外部碎片导致失败（核心案例，必出"失败"）

目的：展示"空闲总量足够，但最大空闲块不足 → 申请失败"，并示范同长平局规则。

```
TOTAL = 90   （注意取 90：三块 30 恰好占满，避免尾部空闲块干扰）
1. alloc A 30   A=[0,30)
2. alloc B 30   B=[30,60)
3. alloc C 30   C=[60,90)                    内存占满
4. free A                                    空闲 [0,30)
5. free C                                    空闲 [0,30)+[60,90)：总量 60，最大块 30，块数 2
6. alloc D 50  → 失败！总量 60 ≥ 50，但最大块 30 < 50（两种策略同样失败，状态不变）
7. alloc E 20  → 同长平局：候选 [0,30) 与 [60,90) 同为 30 → 取低地址
                 E=[0,20)，空闲 [20,30)+[60,90)
8. free B       B=[30,60) 左右皆空闲 → 双侧合并 → [20,90)
9. free E       E=[0,20) 右邻 [20,90) 空闲 → 仅右合并 → [0,90)（完全恢复）
```

观察点：
- 第 6 步失败文案要写明两个数字（总量够 / 块不够）；
- **失败与策略无关**——这是连续分配的本质问题（外部碎片），不是 FF/BF 选得不好，
  这本身就是报告的一个重要结论；
- 第 7 步验证 Best Fit "同长取低地址"规则。

## 三、每步必记录的四项指标

| 指标 | 定义 |
|------|------|
| 空闲总量 | Σ 所有空闲块长度 |
| 最大空闲块 | max 空闲块长度（无空闲块时为 0） |
| 空闲块数量 | 空闲表长度 |
| 申请结果 | 成功（起址）/ 失败（原因） |

## 五、差异标注要求

两策略结果不同的步骤，在 trace 与报告中**显式标出**（如 ★差异步），
写明：该步两策略各选了哪个空闲块、为何不同（候选集与选择标准）。
案例 1 第 5 步即为标准示例。
