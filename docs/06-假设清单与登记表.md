# 06 · 六条核心假设与登记表

> 依据：任务书第 2 页四步法第一步"先提出假设"——每位成员**独立**写一项判断或疑问，并说明理由。
> 本文件记录本组六条主假设的分配，并给出登记表模板。
> 对应评分点：小组"假设与规则 5 分"；个人"针对输入变化提出假设或手工推算 10 分"。

## 一、为什么必须"先"提出假设

假设必须在**跑程序、问模型之前**写下并提交进仓库。`git log` 的提交时间即为留痕证据。
事后补写的假设无法证明"先假设、后验证"，现场追问一步就会露。因此：

1. 先各自写假设 → 提交（此时 `web/` 尚无实现）；
2. 再问模型、再写代码、再跑实验；
3. 最后逐条判定**支持 / 推翻 / 修正**。

## 二、假设与"约定"、"问题"的区别

| 类型 | 例子 | 能否被推翻 |
|------|------|------------|
| **模型约定**（规则设定） | 整数地址、不计管理开销、不做紧缩、低地址端切出 | 不能 |
| **假设**（本题要写的） | "申请失败与选块策略无关" | 能 |
| **研究问题** | "总量足够为什么还会失败？" | 不能（这是提问） |

假设要写成"在某条件下，我认为会发生某现象，因为某机制；若某指标出现某结果则被推翻"。

## 三、六条主假设与负责人

| 编号 | 假设（简写） | 负责人 | 层次 | 主检验案例 |
|------|--------------|--------|------|------------|
| A1 | 申请成败只看最大空闲块，与空闲总量无关 | 陈子俊 | 核心判据 | 案例 3 第 6 步 |
| A2 | 申请失败与策略无关，两策略在同一步失败 | 黄应辉 | 核心判据 | 案例 3 双策略对照 |
| B2 | 最佳适应在所有负载下整体优于首次适应（绝对化，预期被推翻） | 蔡旭迪 | 策略评价 | 案例 1 分歧步 + 反例搜索 |
| B5 | 策略差异会经后续释放合并累积放大 | 梁赫铭 | 策略评价 | 案例 1 第 5–7 步 |
| C1 | 关闭合并后空闲块数持续上升、碎片迅速恶化 | 史一飞 | 合并机制 | 合并开/关对照 |
| D1 | 失败申请若执行切块，会破坏守恒式 | 李志恒 | 实现/反例 | 故意构造错误版本 |

### 逐条要点

**A1（陈子俊）**
- 理由：分配要求地址连续，候选集 $\mathcal{C}(w)=\{F\mid \ell_F\ge w\}$ 只由各块自身长度决定。
- 检验：案例 3 第 6 步（总量 60、最大块 30、申请 50 → 失败）；另做对照——总量 40 中有一块 40，申请 40 → 成功。
- 推翻判据：出现"总量 ≥ 申请量、最大块 < 申请量却成功"，或"总量 < 申请量却成功"。

**A2（黄应辉）**
- 理由：失败发生在进入选块规则之前（候选集为空），与 $\arg\min$ 无关。
- 检验：`case3` 各跑 FF / BF，逐行 diff 两份 trace 的第 6 步。
- 推翻判据：出现"FF 失败而 BF 成功"，且原因是候选集非空、仅选块不同。

**B2（蔡旭迪）**
- 理由（提出时）：每次挑最小的可装下块，剩余碎片最小。
- 检验：案例 1 第 5 步分歧后，比较两策略的空闲块数、最大空闲块；构造"中小申请反复出现"的序列。
- 推翻判据：任一指标（失败次数 / 空闲块数 / 最大块）BF 反而更差。
- 说明：这条是任务书要求"构造能推翻绝对化判断的输入"的落点，须与大模型交互记录呼应。

**B5（梁赫铭）**
- 理由：合并依赖"邻居是否空闲"，邻居归属变化即改变合并结果。
- 检验：案例 1 第 5 步分歧 → 第 7 步 FF 双侧合并、BF 仅左合并。
- 推翻判据：后续步骤中两策略布局重新收敛并保持一致。

**C1（史一飞）**
- 理由：每次释放新增一块空闲区；合并只作用于相邻块，被已分配区隔开的两块永远合不到一起。
- 检验：同一序列跑"合并开/关"两版，统计空闲块数曲线与失败次数；案例 3 第 8、9 步验证全释放后能否恢复为单块。
- 推翻判据：关闭合并后块数不增；或开启合并后外部碎片可被完全消除。

**D1（李志恒）**
- 理由：失败不是分配，状态必须逐字段不变。
- 检验：故意写一版"失败也切块"的错误实现，用三项检查捕获；再测重复释放、释放不存在编号、申请量 ≤ 0 或 > T。
- 推翻判据：错误实现下守恒仍成立（说明检查写漏了）。
- 说明：全组唯一的"故意造 bug"实验，对应评分点"对照、反例或故障实验"。

## 四、登记表模板

每人一份，存于 `experiments/hypotheses/<编号>-<姓名>.md`，内容如下：

```markdown
# 假设 <编号>：<一句话标题>

- 提出人：<姓名> <学号>
- 提出时间：YYYY-MM-DD（须早于实验运行与模型咨询，以 git 提交时间为证）
- 负责人分工：<该成员在小组中的职责>

## 1. 假设表述
<完整、具体、可证伪的判断，一句话说清对象、条件与比较对象>

## 2. 理由
<机制层面的原因：为什么预期会出现这个现象>

## 3. 预期现象
<如果假设成立，程序轨迹中应观察到什么；给出具体指标与数值预期>

## 4. 检验方式
- 输入：<experiments/inputs/....json>
- 操作：<跑哪个策略、对比哪几行>
- 记录：<traces 文件、指标表位置>

## 5. 推翻判据
<出现什么数据即判定假设不成立>

## 6. 核验结论
- 判定：支持 / 推翻 / 修正为 ___
- 证据位置：<trace 行号、指标表、人工推演表路径>
- 差异出现的位置与原因：___
- 认识变化：<核验后我的判断如何改变，还有什么不能据此推出>
```

## 五、与报告、个人分析的关系

| 位置 | 放什么 |
|------|--------|
| 报告表 1（六条待检验假设及其提出人与检验方式） | 六条的**汇总**（已填好，姓名与编号一致） |
| 报告第 4 节 | 逐条给出**支持/推翻的证据**（案例 1、3 的轨迹与指标） |
| 报告附录 B | 六人**分工、假设编号、证据位置** |
| `experiments/hypotheses/` | 每人的**完整登记表**（原始留痕） |
| `individual/` 个人分析 | 各人只写**自己那条**：初始假设 → 亲自验证 → 认识变化 |
