# 04 · 现场验收与答辩准备

> 任务书第 14 页第六节给出了现场验收示例。老师验收时大概率照此出题：
> **现场改参数 → 先手工画布局 → 再运行验证 → 解释原理**。

## 一、验收原文

> 改变一次申请大小，或交换两次释放的顺序，先画出关键步骤后的内存布局；
> 解释为什么"最佳适应"不等于所有负载下的整体效果最佳。

## 二、怎么应对：三步答法

1. **先手画**：不碰程序，在纸上按规则逐步推演布局（这是个人分的关键）；
2. **再运行**：程序验证，一致则确认，不一致则当场定位差异步骤与原因；
3. **后解释**：用"候选集 + 选择标准"的语言说明策略差异。

## 三、必背要点（个人考核 30 分高频考点）

### 3.1 为什么"总量够"还会失败？
分配要求**地址连续**。反复分配释放后，空闲内存被已分配区**分隔成互不相邻的小块**
（外部碎片）。申请 W 成功的充要条件是：**存在一块空闲块长度 ≥ W**，
即 `最大空闲块 ≥ W`，而不是 `空闲总量 ≥ W`。

### 3.2 为什么"最佳适应"≠ 整体最佳？
- BF 的"最佳"只指**本次**选择：在能装下的块里选最小，使本次剩余碎片最小；
- 副作用：它**优先消耗恰好够用的小块**，把大块留到最后——但长期看它把大块
  也逐步切碎，产生大量**微小到几乎不可用**的剩余块；
- FF 按地址顺序用低地址端，高地址端容易保持大块完整；
- 结论都是**针对具体负载**的，没有普适最优（这也是报告"结论与局限"的核心）。

### 3.3 合并边界（最常追问）
释放区 X，地址区间 `[s, s+len)`：
- 左邻空闲（某空闲块终点 = s）→ 吸收左侧；
- 右邻空闲（某空闲块起点 = s+len）→ 吸收右侧；
- 两侧都空闲 → **三块合一**；
- 实现：插入后顺序扫描一遍空闲表做相邻合并，天然覆盖全部情形。

### 3.4 失败操作为什么必须"状态不变"？
失败不是分配；若失败还切了块，守恒与布局都会被破坏。
实现上应**先找到可装下的块，找不到直接返回失败**，不做任何修改。

### 3.5 改申请大小 / 换释放顺序会怎样？（现场常改的点）
- 改申请大小：可能从"失败"变"成功"或反之，关键是**最大空闲块**是否跨越阈值；
- 交换释放顺序：影响合并能否发生——相邻块必须**都处于空闲状态**才能合并；
  先释放中间块再释放两侧 → 三合一；顺序不对可能同样最终状态但路径不同，
  或中间块被新申请抢占导致无法合并。

## 五、老师可能的追问清单

| 追问 | 答题要点 |
|------|----------|
| 为什么不做紧缩？ | 任务书模型简化；紧缩需要重定位支持，实系统开销大 |
| 空闲块怎么组织？ | 按地址排序的链表/数组；FF 顺序扫，BF 全扫取最小 |
| 同长怎么选？ | BF 同长取低地址（任务书规定）；FF 天然取第一个 |
| 重复释放怎么办？ | 报错且状态不变；靠唯一编号查重 |
| 已分配区为什么不会重叠？ | 每次分配只从空闲区切出，已分配区互斥产生 |
| 守恒式是什么？ | Σ已分配 + Σ空闲 = TOTAL，每步自动检查 |
| 这个模型与真实 OS 差在哪？ | 无伙伴系统/Slab、无页级管理、无紧缩、无管理开销、整数地址简化 |
| BF 什么场景反而差？ | 中小申请反复出现时，大块被逐步切碎，大申请失败率升高 |
